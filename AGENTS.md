## Routing and meeting search behavior

- The meeting engine is in `backend/src/services/meet.services.ts`.
- Current meeting search version is `MEET_CACHE_VERSION = "v5"` and uses in-memory request/result caching keyed by bucketed origin coordinates.
- Route seeds are now built from OTP plans in both directions, using non-car modes only: WALK, BUS, RAIL, SUBWAY.
- The seed flow asks OTP for up to three itineraries from A to B and B to A, extracts timed points from legs/stops, compares forward and reverse route points, and chooses the first three transit-balanced touch seeds.
- If OTP route seeding fails or returns too few useful points, the engine falls back to the previous geometric midpoint/offset seeds so meet search still works.
- POI lookup expands radius circles around the three touch seeds. It increases radius until there are enough named places overall and at least a minimum count in every touch circle, then continues with existing segregation/ranking.
- Meeting POIs come from Overpass through `poi.services.ts`; results are filtered to service-area bounds before caching.
- Overpass endpoint probing now runs available endpoints in parallel instead of sequentially, so an outage costs roughly one timeout window.
- If live Overpass POI lookup fails or returns no named places, the meet engine falls back to a curated Mumbai/Mira Bhayandar venue set inside `meet.services.ts`, filtered by the same expanding seed radii and ranked through the normal scoring pipeline.
- Ranking still considers balanced travel time, max travel time, average travel time, category quality, and category diversification.
- Route duration scoring uses OTP duration when available and distance fallback when OTP is unavailable.
- Frontend and detail route requests should use local transit without car: `{ bus: true, rail: true, subway: true, car: false }`.

## Latest meet-search bug findings

- Symptom investigated: OTP logged `Cost mismatch` warnings and `TemporaryVerticesContainer Couldn't link (...)`, while meet search showed no results.
- Conclusion: the OTP warnings are noisy and can indicate routes or temporary points that OTP cannot link, but the reproduced empty-results failure was caused by all Overpass endpoints timing out. The service then returned an empty list because there was no non-network POI fallback.
- Fixes applied: reduced meet seed/POI timeout windows, made Overpass endpoint checks parallel, relaxed the three-circle requirement so one unproductive touch circle cannot starve all results after max expansion, and added the curated local venue fallback.
- Verification performed directly against `findMeetPoints` with in-bounds Mumbai/Mira test pairs, including the coordinate from the OTP warning `(19.1429570637995, 72.76692793131284)`. With all Overpass endpoints timing out, the service returned non-empty results: 5 results for the warning-coordinate case and 7 results for Juhu-to-Mira Road.

## Autocomplete behavior

- Backend autocomplete route: `backend/src/routes/search.routes.ts`.
- Client autocomplete helper: `frontend/src/lib/locationSearch.js`.
- Search is geo-locked with `SERVICE_AREA_BOUNDS` and `SERVICE_AREA_NAMES`; Photon requests include a Mumbai/Mira Bhayandar query and bbox.
- Suggestions combine curated local places, Photon results, and popularity hits.
- Backend keeps an in-memory search cache with TTL and pending-request de-duplication.
- Backend also tracks selected suggestions through `POST /api/search/select`; popular selected places rank higher in later search responses.
- Frontend keeps a localStorage suggestion cache and local popularity map so repeated searches feel instant for the same browser.
- `MeetPage.jsx` records popularity when a suggestion is selected for either origin.

## Results/detail performance notes

- `ResultsPage.jsx` no longer calls the public OSRM driving API for decorative preview lines; it draws immediate straight preview lines between origins and the midpoint.
- Results route data cache is capped to a small number of entries before being stored for navigation restoration.
- Detail and results route requests use non-car local transit by default.
- If detail receives no route data, it can still fetch routes itself; if route data is passed from results, it renders immediately.
