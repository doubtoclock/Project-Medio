Env files worth knowing:

- `frontend/.env` is local dev and points the API at `http://localhost:5001`. Never bake that into a shipped build.
- `frontend/.env.production` (gitignored) overrides the API origin for `npm run build`, so both the web and the APK target the deployed backend. This is what fixed the shipped-app failure where every API call went to the phone's own `localhost`.
- `backend/.env` is local dev and must NOT set `OTP_*` to a localhost address if the backend is deployed.
- `.env.example` files are the only versioned env documentation; keep deploy-critical notes in the comments there.

## Routing and meeting search behavior

- The meeting engine is in `backend/src/services/meet.services.ts`.
- Current meeting search version is `MEET_CACHE_VERSION = "v5"` and uses in-memory request/result caching keyed by bucketed origin coordinates.
- Route seeds are now built from OTP plans in both directions, using non-car modes only: WALK, BUS, RAIL, SUBWAY.
- The seed flow asks OTP for up to three itineraries from A to B and B to A, extracts timed points from legs/stops, compares forward and reverse route points, and chooses the first three transit-balanced touch seeds.
- If OTP route seeding fails or returns too few useful points, the engine falls back to the previous geometric midpoint/offset seeds so meet search still works.
- POI lookup expands radius circles around the three touch seeds. It increases radius until there are enough named places overall and at least a minimum count in every touch circle, then continues with existing segregation/ranking.
- Meeting POIs come from Overpass through `poi.services.ts`; results are filtered to service-area bounds before caching.
- Overpass endpoint probing now runs available endpoints in parallel instead of sequentially, so an outage costs roughly one timeout window.
- If live Overpass POI lookup fails or returns no named places, the meet engine falls back to a curated Mumbai/Mira Bhayandar venue set inside `meet.services.ts`, filtered by the same expanding seed radii and ranked through the normal scoring pipeline.
- Ranking still considers balanced travel time, max travel time, average travel time, category quality, and category diversification.
- Route duration scoring uses OTP duration when available and distance fallback when OTP is unavailable.
- Frontend and detail route requests should use local transit without car: `{ bus: true, rail: true, subway: true, car: false }`.

## Latest meet-search bug findings

- Symptom investigated: OTP logged `Cost mismatch` warnings and `TemporaryVerticesContainer Couldn't link (...)`, while meet search showed no results.
- Conclusion: the OTP warnings are noisy and can indicate routes or temporary points that OTP cannot link, but the reproduced empty-results failure was caused by all Overpass endpoints timing out. The service then returned an empty list because there was no non-network POI fallback.
- Fixes applied: reduced meet seed/POI timeout windows, made Overpass endpoint checks parallel, relaxed the three-circle requirement so one unproductive touch circle cannot starve all results after max expansion, and added the curated local venue fallback.
- Verification performed directly against `findMeetPoints` with in-bounds Mumbai/Mira test pairs, including the coordinate from the OTP warning `(19.1429570637995, 72.76692793131284)`. With all Overpass endpoints timing out, the service returned non-empty results: 5 results for the warning-coordinate case and 7 results for Juhu-to-Mira Road.

## Autocomplete behavior

- Backend autocomplete route: `backend/src/routes/search.routes.ts`.
- Client autocomplete helper: `frontend/src/lib/locationSearch.js`.
- Search is geo-locked through the data-driven `SERVICE_AREAS` config in `backend/src/utils/service-area.ts`. The current default service area is `mumbai-mira-bhayandar`; adding another city should mean adding a new config entry with bounds, accepted names, and Photon query metadata instead of changing search logic.
- Search still uses Photon as the primary external geocoder. Photon requests use the configured bbox and the raw user query; appending city words remains avoided because it corrupts Photon's ranking.
- The backend now has a persistent shared Mongo place cache in `backend/src/models/cached-place.ts`. Cached places belong to a `serviceAreaId`, not a user, and are reusable by every user.
- Cached places store canonical names, normalized names, aliases, address parts, search tokens, character grams, source/sourceId, coordinates, selection counts, `lastSeenAt`, and `expiresAt`.
- Cached-place indexes include service-area/name, service-area/aliases, service-area/tokens, service-area/grams, source/sourceId, coordinate lookup, text search fields, and a TTL index on `expiresAt`.
- Autocomplete flow is now: normalize the query, fuzzy-search the shared place cache first, return strong cache hits immediately, otherwise query Photon, normalize/dedupe/filter Photon results, persist canonical Photon places and aliases, then confidence-rank combined cache/Photon/curated/popular results.
- Fuzzy fallback candidate generation must dedupe broadly before ranking, not cap to the eight public results first. A past regression caused typo queries like `versiva`, `virsovaa`, and `virsowa` to miss Versova because Versova appeared after the first eight curated entries.
- Do not cache arbitrary typo strings as standalone places. Typos should map to canonical cached places through aliases/search grams/fuzzy scoring. User-specific search caching should only be used later for personalization or recents.
- Suggestions preserve the existing API response shape: `{ name, lat, lng }`.
- Suggestions combine shared cached places, curated local places, Photon results, and popularity hits; display names prefer locality/suburb over ward-code districts, and `Mira-Bhayander` is normalized to `Mira Bhayandar`.
- Backend still keeps a small in-memory search response cache with TTL, limits, and pending-request de-duplication for speed, but the shared place cache is checked first.
- Backend tracks selected suggestions through `POST /api/search/select`; popular selected places rank higher in later search responses and the shared cached-place selection count is updated when possible.
- Frontend keeps a localStorage suggestion cache and local popularity map; the cache is reused for longer typed prefixes (e.g. a cached `and` query serves `andheri`), so repeated searches feel instant for the same browser. Cached frontend suggestions must be filtered with typo-aware matching, otherwise a backend fuzzy result can be hidden on the next exact cached lookup.
- `MeetPage.jsx` records popularity when a suggestion is selected for either origin.

## Shared meeting App Links

- Shared meeting URLs use `https://medio.mywire.org/share/:shareId`; the React route is `/share/:shareId` and must remain usable in a browser as a fallback.
- `SharedLinkPage.jsx` loads the saved share and renders the same `DetailPage` layout as the original meeting point, swapping origin A/B and their route data for the recipient. Keep the bottom Navigate button consistent on both views.
- Android App Links cover `https://medio.mywire.org/share/` and `https://www.medio.mywire.org/share/`. The generated `frontend/android/` directory is gitignored, so after `npx cap sync android`, run `npm run configure:android-links` from `frontend/` (or `npm run sync:android`, which performs both steps) to add the verified link intent filter.
- `frontend/src/App.jsx` handles cold and warm incoming links through `@capacitor/app`; accept only HTTPS links on `medio.mywire.org` or `www.medio.mywire.org` with the `/share/:shareId` path.
- `frontend/public/.well-known/assetlinks.json` must be deployed at `https://www.medio.mywire.org/.well-known/assetlinks.json` with `application/json` and no redirect. The apex currently redirects to `www`, which prevents Android from verifying the apex host. The file's SHA-256 fingerprint matches the release APK signing certificate. If Play App Signing or a signing-key rotation changes the installed app certificate, include that certificate fingerprint too.
- Android users need an updated install containing the App Link intent filter. Verify domain association after deployment with Android's `pm get-app-links com.medio.app` or `assetlinks` verification tools; links may continue to open in the browser until association succeeds.

## Results/detail performance notes

- `ResultsPage.jsx` no longer calls the public OSRM driving API for decorative preview lines; it draws immediate straight preview lines between origins and the midpoint.
- Results route data cache is capped to a small number of entries before being stored for navigation restoration.
- Detail and results route requests use non-car local transit by default.
- If detail receives no route data, it can still fetch routes itself; if route data is passed from results, it renders immediately.

## Deployment topology (easy to get wrong)

- The live backend is the Render service `medio-api-y19r`. `medio-api-832i` also exists but is an older copy; treat it as stale.
- The web app on `https://medio.mywire.org` must have `VITE_BACKEND_URL` pointed at the live backend host. A console error naming `medio-api-832i` means the deployed frontend is still calling the old service, not an OTP problem.
- Render free services sleep. Cold starts measured ~42s, so an apparently hung first request is often just a wake-up, not a bug.
- OTP runs on a separate always-on Oracle Cloud VM in Mumbai. `render.yaml` carries the `OTP_BASE_URL` host for it; treat that value as sensitive infrastructure detail and do not copy it into docs or logs.
- If `/api/otp/route` returns `502` in well under a second, the deployed backend is almost certainly still using the `localhost:8080` code default for `OTP_BASE_URL` rather than the Oracle host. A genuinely slow/unreachable OTP fails near the 30s controller timeout instead. Quick check: `0.3s` failure means env not applied; `~2-3s` success means it is wired correctly.
- Blueprint env values only apply when the service is created. Edits made in the Render dashboard, or a service predating a `render.yaml` line, win over the file. Always confirm the effective value in the dashboard rather than trusting `render.yaml`.
- Verify the Oracle OTP directly before blaming the backend: a `plan` query with Mumbai coordinates should return `200` and an `itineraries` array in ~1-3s.
- The OTP warmup query in `backend/src/server.ts` is a walk-only `plan` request, not `{ routers { routerId } }`. The deployed OTP rejects a `routers` field, so the old query reported a healthy service as broken.
- The `medio-otp` service defined in `render.yaml` is dead on Render and should be deleted. Its `-Xmx350m` free-plan heap cannot hold the Mumbai graph, which needs roughly 2GB in memory; the real OTP lives on the Oracle VM.
- `OTP_ISOCHRONE_URL` points at the REST isochrone endpoint that OTP 2.x removed, so it always 404s and the surface-intersection fallback in `surface.services.ts` is effectively dead code. Reimplement it against the GraphQL API or delete the path.
- `meet.services.ts` uses a 1s POI timeout while Overpass queries can run for 25s, so live POI lookup usually times out and results lean on the curated venue fallback. Raising the timeout trades latency for fresher POIs.

## Android release builds

- The native project is `frontend/android/`, generated by Capacitor 8 and gitignored. Treat it as generated, not hand-authored source.
- Android Gradle Plugin 8.13 needs **JDK 21**. The machine's default JDK 25 breaks it, so builds must run with `JAVA_HOME=/opt/homebrew/opt/openjdk@21`.
- The SDK lives at `~/Library/Android/sdk`; `frontend/android/local.properties` points at it. Platform `android-36` and build-tools `36.0.0` are installed.
- Gradle output directories are symlinked to `frontend/android/.build-out/` because builds run on an external volume that previously lost its mount. If a build reports a missing output dir, re-check those symlinks before anything else.
- Release signing uses a PKCS12 keystore stored outside the repo with the password in a sibling `PASSWORDS.txt`; both are `chmod 600`. `frontend/android/release-signing.properties` references them and is gitignored. Never commit keystore material or the password.
- Always verify an APK with `apksigner verify` plus `aapt` for package/version/targetSdk. `apksigner verify --print-certs` is the check that proves a build is actually signed by the expected key.
- Keep the shipped build honest: confirm the built bundle contains the deployed API origin and no `localhost:5001` string, since a silently wrong `VITE_BACKEND_URL` ships an app that only fails on device.
- Canonical build outputs live under `frontend/android/app/build/outputs/`; copies in `releases/` are conveniences and can go stale after a rebuild. Copy fresh artifacts rather than trusting the folder.

## Google sign-in

- Plugin: `@capawesome/capacitor-google-sign-in`. Its `initialize` ignores `serverClientId`, so the plugin's `clientId` field must be the **web** OAuth client ID; the server client ID belongs in `VITE_GOOGLE_SERVER_CLIENT_ID` used by `LoginPage.jsx`.
- Client IDs live in env (`VITE_GOOGLE_CLIENT_ID`, `VITE_GOOGLE_SERVER_CLIENT_ID`) rather than hardcoded in the page, and must match the backend `GOOGLE_CLIENT_ID`.
- The Android OAuth client in the Google console must use package `com.medio.app` with the release SHA-1/SHA-256 of the upload key. A package-name or fingerprint mismatch surfaces as an instant `GetCredentialCancellationException`, which looks like a user cancellation but is a server-side config failure.
- `frontend/android/app/google-services.json` is filled from the `medio-487212` (number `943070343124`) project and holds the web OAuth client. Do not confuse it with the separate `medio-50405` Firebase project.
- Native library versions in `frontend/android/variables.gradle` are pinned deliberately: `googleid 1.2.1`, `androidx.credentials 1.6.0`, `play-services-auth 21.6.0`. Bumping them pulled in a newer `GetSignInWithGoogleOption`, so keep them explicit instead of inheriting defaults.
- Because the app is still in testing, the OAuth consent screen must list test users or sign-in fails for accounts outside the test list.
- Debug Google sign-in through `adb logcat`; the frontend only surfaces the reason code, not the underlying exception.
